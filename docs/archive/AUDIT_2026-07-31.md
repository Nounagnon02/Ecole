# 1. SÉCURITÉ

## 🔴 CRITIQUE

### S1 — Tout directeur contourne l'intégralité des contrôles de rôle

`app/Http/Middleware/CheckRole.php:26`

```php
if (!in_array($request->user()->role, $roles)) {
    if ($request->user()->isAdmin()) {   // ← échappatoire
        return $next($request);
    }
    return response()->json([...], 403);
}
```

`User::isAdmin()` (`app/Models/User.php`) renvoie `true` pour `directeur`, `directeurM`, `directeurP`, `directeurS`, `super-admin`. Conséquence : **le middleware `role:` ne bloque jamais un directeur**, quel que soit le rôle exigé.

Impact concret :
- `role:super-admin` sur `POST /api/ecoles/provision` → un directeur provisionne des écoles.
- `role:infirmier` sur `/api/infirmier/dossiers-medicaux` → accès aux dossiers médicaux.
- `role:admin,super-admin` sur `/api/admin/utilisateurs` → voir/désactiver/supprimer **les utilisateurs de toutes les écoles** (le modèle `User` est explicitement exclu du scope tenant, cf. `app/Traits/BelongsToEcole.php:12`).

**Correction :** supprimer l'échappatoire. Si un super-admin doit tout voir, l'ajouter explicitement : `if ($user->role === 'super-admin') return $next($request);` — et jamais `directeur`.

### S2 — CORS reflète n'importe quelle origine avec `Allow-Credentials: true`

`app/Http/Middleware/CorsMiddleware.php:17-24`

```php
$origin = $request->header('Origin', '*');
'Access-Control-Allow-Origin'      => $origin,
'Access-Control-Allow-Credentials' => 'true',
```

Ce middleware est global (`app/Http/Kernel.php`, 2ᵉ position) et **`Illuminate\Http\Middleware\HandleCors` est absent de la pile** — la whitelist de `config/cors.php` (correctement écrite, elle) n'est donc **jamais appliquée**. C'est du code mort.

Avec l'auth par cookie de session Sanctum SPA, n'importe quel site visité par un utilisateur connecté peut lire toute l'API en son nom : notes, dossiers médicaux, paiements, messagerie. `SameSite=lax` (`config/session.php:199`) ne protège pas ici.

**Correction :** supprimer `CorsMiddleware` de la pile et rétablir `\Illuminate\Http\Middleware\HandleCors::class`, qui lit `config/cors.php`.

### S3 — Fraude au paiement : un paiement se marque « complété » sans vérification

`app/Http/Controllers/PaymentController.php:118-126`

```php
// Fallback : marquer comme complété (à adapter selon le flux réel)
$payment->update([
    'status'         => 'completed',
    'paid_at'        => now(),
    'payment_method' => 'mobile_money',
]);
```

Ce bloc s'exécute **dès que la vérification provider échoue ou que `transaction_id` est nul**. La route `POST /api/payments/mobile-money` (`routes/api/services.php`) n'a ni contrôle de rôle ni contrôle de propriété — seulement `throttle:paiements`.

Un élève authentifié peut donc solder la scolarité de n'importe qui :
```
POST /api/payments/mobile-money  {"payment_id": 42, "phone_number":"x", "operator":"mtn"}
```

**Correction :** ne jamais passer `completed` sans confirmation provider ; réserver la transition d'état au webhook signé ; ajouter un contrôle de propriété sur `payment_id`.

### S4 — Messagerie : identité fournie par le client

`app/Http/Controllers/MessageController.php:12, 30, 72, 83, 107, 144`

```php
$userId = $request->user_id;   // ← input client, pas auth()->id()
```

Six méthodes prennent l'identité dans la requête. Résultat :
- `GET /api/messages/received?user_id=7` → boîte de réception de l'utilisateur 7.
- `GET /api/messages/sent?user_id=7` → messages envoyés.
- `GET /api/messages/conversation/{id}?user_id=7` → conversation complète.

Et `store()` (ligne 46) valide `expediteur` comme un champ ordinaire → **usurpation d'expéditeur** : envoyer un message signé « Directeur » à tous les parents.

`markAsRead($id)` (ligne 63) ne vérifie aucune propriété.

Aggravant : tout le contrôleur passe par `DB::table('messages')`, ce qui **court-circuite le global scope `BelongsToEcole`** du modèle `Message` → fuite inter-établissements. `getUsers()` expose la liste + emails de tous les enseignants, toutes écoles confondues.

**Correction :** remplacer systématiquement par `auth()->id()`, retirer `expediteur` du validate, utiliser le modèle `Message` au lieu de `DB::table`.

### S5 — Fuite inter-tenant : toutes les écoles exposées à tout directeur

`app/Http/Controllers/EcoleController.php:17, 52-57`

```php
public function index()  { return response()->json(['data' => Ecole::all()]); }
public function show(Ecole $ecole) {
    return response()->json(['data' => $ecole->load(['users','eleves','enseignants','classes'])]);
}
```

`Ecole` n'utilise pas `BelongsToEcole` (normal, c'est la racine du tenant) mais la route `apiResource('ecoles')` est ouverte à `role:directeur,super-admin`. Un directeur peut donc **lister toutes les écoles clientes, dumper l'intégralité de leurs utilisateurs/élèves/enseignants, les modifier et les supprimer** (`destroy`, avec `cascadeOnDelete` sur `ecole_id` → destruction en cascade des données).

**Correction :** restreindre `index`/`show`/`update`/`destroy` à `super-admin` ; pour un directeur, ne renvoyer que sa propre école.

### S6 — Module universitaire hors du modèle multi-tenant

Aucune des tables `universites`, `facultes`, `departements`, `filieres`, `etudiants`, `inscriptions`, `semestres`, `diplomes` ne porte de colonne `ecole_id`, et **aucun des 12 modèles `app/Models/universite/*` n'utilise le trait `BelongsToEcole`**. Elles sont également absentes de la migration de rattrapage `2025_11_01_041712_ecole_add_id.php`.

Toutes les routes `/api/universite/*` opèrent donc sur un espace de données global partagé : un recteur de l'université A lit et modifie les étudiants, notes et diplômes de l'université B.

Même problème, moindre portée, sur : `cahier_de_textes`, `evenements`, `payment_histories`, `vehicules`, `trajets_transport`, `abonnements_transport`.

**Correction :** ajouter `ecole_id` (ou `universite_id` scopé) + le trait sur ces modèles.

### S7 — Upload de fichier sans restriction de type, exposé publiquement

`app/Http/Controllers/DevoirController.php:130, 146`

```php
'fichier' => 'nullable|file|max:10240',              // aucun mimes:
$path = $request->file('fichier')->store('devoirs/'.$id, 'public');
```

Route `POST /api/devoirs/{id}/soumettre`, ouverte à `role:eleve`. Un élève peut déposer un `.html` ou un `.svg` servi depuis l'origine de l'application → **XSS stocké** permettant le vol de session de l'enseignant qui ouvre le devoir. Si le lien symbolique `storage/` se trouve sous une racine exécutant PHP, un `.php` donne une RCE.

Même schéma sur `Central/SettingsController.php:103` (`mimes:png,jpg,svg` — le SVG est un vecteur XSS).

**Correction :** whitelist stricte (`mimes:pdf,docx,jpg,png`), stockage sur disque privé + route de téléchargement authentifiée, `Content-Disposition: attachment`.

# 2. PERFORMANCE

## 🔴 CRITIQUE

### P1 — Chaque requête SQL est journalisée, en production incluse

`app/Providers/AppServiceProvider.php:24-27`

```php
DB::listen(function ($query) {
    Log::info("SQL: " . $query->sql);
    Log::info("Bindings: " . implode(", ", $query->bindings));
});
```

Aucune garde d'environnement. Conséquences cumulées :
- **2 écritures disque synchrones par requête SQL.** Un dashboard à 40 requêtes = 80 I/O de log en plus.
- `storage/logs/laravel.log` croît sans limite → saturation disque.
- Les bindings contiennent des **données personnelles en clair** : emails, téléphones, notes, données médicales, et les hachages bcrypt lors des créations de compte. C'est aussi un problème RGPD.

**Correction :** supprimer le bloc, ou l'encadrer par `if (app()->environment('local'))`.

## 🟠 ÉLEVÉ

### P2 — Invalidation de cache inopérante

`app/Http/Controllers/DashboardController.php:30` vs `:63`

```php
Cache::remember('dashboard_directeur_' . $ecoleId, 300, ...)   // écriture
Cache::forget('dashboard_directeur');                          // suppression — mauvaise clé
```

`POST /dashboard/directeur/invalidate-cache` ne supprime rien. Le dashboard reste figé 5 minutes après toute saisie de notes ou inscription.

### P3 — Endpoints non bornés

- `getDashboardData` charge **tous** les élèves, matières, classes, séries avec relations en une réponse. À 2 000 élèves, la charge utile se compte en méga-octets, et le `Cache::remember` sur driver `file` (défaut `.env.example`) sérialise l'ensemble à chaque miss.
- `EcoleController::show` → `load(['users','eleves','enseignants','classes'])` sans limite.
- `ExportController::exportFinances` → `PaiementEleve::with('eleve.user')->get()` : tout l'historique en mémoire.
- 108 `->get()` contre 21 `paginate()` dans les contrôleurs.

### P4 — N+1

- `DashboardController::parent` : `with(['classe','notes.matiere'])` puis `$child->user->name` — la relation `user` n'est pas préchargée → 1 requête par enfant.
- `ParentController::bulletins:87` : requête `Notes` par enfant dans une boucle.
- `MessageController::getConversations:124-134` : 1 à 2 requêtes par conversation.

### P5 — Index insuffisants

8 migrations sur 88 déclarent des index. Non couverts alors que fortement filtrés : `messages(destinataire, lu)`, `notes(matiere_id, periode)`, `users(role, ecole_id)`, `evenements(date)`. La migration `2025_11_01_041712` a bien ajouté un index sur `ecole_id` — c'est le bon réflexe, à étendre.

## 🟡 MOYEN

- `Schema::defaultStringLength(191)` global : hérité de MySQL 5.5, pénalise inutilement les colonnes modernes.
- `Ecole_frontend` : `xlsx`, `jspdf`, `pdfjs-dist`, `recharts`, `framer-motion` en dépendances directes. Le `manualChunks` de `vite.config.js` les isole correctement, mais avec `chunkSizeWarningLimit: 250` le budget est probablement dépassé — à mesurer.
- Retry automatique sur 429 dans l'intercepteur Axios (`api-client.js`) : réémet **une seule fois** sans backoff exponentiel — risque d'amplification sous charge.

**Points positifs :** code splitting et lazy loading corrects côté React, chunks vendor séparés, TanStack Query avec `staleTime` 5 min, rate limiters différenciés par domaine métier (auth / paiements / exports / webhooks / IA), cache offline IndexedDB.

# 3. FONCTIONNEL

## 🔴 BLOQUANT

### F1 — Toute la couche SaaS est du code mort

`app/Providers/TenancyServiceProvider.php` **n'est pas déclaré dans `config/app.php`** (le projet utilise la structure Laravel 10 : `bootstrap/app.php` legacy, tableau `providers`, pas de `bootstrap/providers.php`). Et `routes/central.php` n'est référencé **nulle part** dans le code.

Sont donc injoignables :
- `routes/central.php` : gestion des tenants, plans, abonnements, modules, facturation, white-label, analytics globales, onboarding public — soit ~25 endpoints.
- `routes/tenant.php` : tout le préfixe `/api/v1/`, **y compris les 6 endpoints IA EduPilot** (`/ia/chat`, `/predictive`, `/lesson-plan`, `/tutor`, `/parent-assistant`, `/analyze-results`).

Les contrôleurs `Central/*`, les modèles `SaaS/*`, leurs migrations et `tests/Feature/SaaS/*` existent — mais aucune route ne les atteint. Les tests SaaS échouent nécessairement en 404.

**Correction :** enregistrer `App\Providers\TenancyServiceProvider::class` dans `config/app.php` et charger `routes/central.php` depuis `RouteServiceProvider::boot()`.

### F2 — L'application mobile ne peut pas s'authentifier

`Ecole_mobile/src/services/api.js:34` attend un Bearer token depuis `AsyncStorage`. Or **`createToken()` n'apparaît nulle part dans le backend** (`grep -rn createToken app/ routes/` → aucun résultat). `AuthController::connexion` fait `Auth::login($user)` et renvoie `{user, role, ecole_id, redirect_to}` — sans token.

L'app mobile ne recevra jamais de token, l'en-tête `Authorization` restera vide, et toute route `auth:sanctum` répondra 401.

**Correction :** émettre `$user->createToken('mobile')->plainTextToken` quand le client n'est pas stateful.

### F3 — Calcul de moyennes faux + code inaccessible

`app/Http/Controllers/BulletinController.php:59-71`

```php
$nb = 0;
if ($notes->has('Devoir1') && ...) $nb++;
if ($notes->has('Devoir2') && ...) $nb++;
if ($notes->has('Interrogation') && ...) $nb++;
$nb = $nb > 0 ? $nb : 1;

$moyenne = ($noteDevoir1 + $noteDevoir2 + $moyenneInterros) / 3;  // ← $nb ignoré
```

`$nb` est calculé puis jamais utilisé : la division est codée en dur sur 3. Un élève noté uniquement sur Devoir1 (15/20) obtient **5/20**. Les moyennes trimestrielles du secondaire sont fausses dès qu'une évaluation manque.

Aggravant : les deux branches du `if/else` retournent, ce qui rend **tout le bloc « Cas Maternelle/Primaire » qui suit (lignes 84-108) inaccessible** — les moyennes maternelle/primaire renvoient systématiquement 0.

### F4 — Deux fonctionnalités plantent en erreur 500 (classes non importées)

| Emplacement | Problème |
|---|---|
| `ClassesController.php:24` | `event(new Registered($classe))` — `Registered` n'est pas importé → résolu en `App\Http\Controllers\Registered`, inexistant → `Error` fatale. Non rattrapée par le `catch (\Exception)`. **La création de classe échoue systématiquement.** |
| `AuthController.php:100, 108, 110` | `Eleve`, `UserParent`, `Enseignant` non importés → même mécanisme. **L'inscription d'un élève, d'un parent ou d'un enseignant échoue systématiquement** (seuls les rôles sans profil passent). |

Bonus : `ClassesController::series():BelongsToMany` (ligne 55) est une méthode de relation Eloquent collée dans un contrôleur — `$this->belongsToMany()` y est indéfini.

## 🟠 ÉLEVÉ

### F5 — Flux multi-écoles à moitié implémenté

Le front (`auth-store.js:76-88`) attend `data.schools` et `data.temp_token` pour afficher l'écran de choix d'établissement. `AuthController::connexion` ne renvoie ni l'un ni l'autre. `selectSchool` envoie `token: pendingToken`, que le backend ignore (`AuthController.php:148`). Fonctionnalité inaccessible.

De plus, si `$user->ecole_id` est `null`, `selectSchool` accepte **n'importe quel `ecole_id`** (ligne 157).

### F6 — Validation contournée sur la mise à jour d'élève

`app/Http/Controllers/EleveController.php:105-113`

```php
$validated = $request->validate([...]);            // name, prenom, class_id, serie_id
$user->update($request->only(['name','prenom','email']));      // email non validé
$eleve->update($request->only([...,'numero_matricule']));      // matricule non validé
```

`email` et `numero_matricule` échappent au `validate()` : format libre et doublons possibles, alors que la création impose `unique:`. Corruption d'unicité du matricule.

## 🟡 MOYEN

- **Versionnement d'API absent** : `CLAUDE.md` impose `/api/v1/`, les routes actives sont sur `/api/`. Le seul `/api/v1/` existant est dans les fichiers de routes non chargés (F1).
- **Documentation divergente** : `CLAUDE.md` annonce Laravel 10, `composer.json` requiert `laravel/framework: ^11.0`, la CI est intitulée « Laravel 11 ».
- **`ecole_id` reste `nullable` partout** sans backfill ni contrainte `NOT NULL` (`2025_11_01_041712_ecole_add_id.php`, note en commentaire). Une ligne à `ecole_id = NULL` devient invisible (le global scope filtre dessus) — orpheline silencieuse.
- **`cascadeOnDelete` sur `ecole_id`** : supprimer une école détruit définitivement toutes ses données, sans soft-delete ni sauvegarde.
- **Couverture de tests faible** : 18 fichiers PHP pour 67 contrôleurs ; 3 fichiers front pour 128 sources. Aucun test sur les paiements réels, le calcul de bulletin, ou l'isolation tenant — précisément les zones où sont les défauts ci-dessus.
- **`Ecole_desktop`** ne contient que `main.js`, `preload.js`, `package.json` : ni icône (`ICON_PATH` pointe vers un `icon.png` absent), ni build, ni auto-updater malgré la mention en en-tête.
- **`app/Modules/Central`** : répertoire présent mais non relié à l'autoload applicatif.

# Seconde passe — raisonnement et cohérence (2026-08-03)

Après la remédiation initiale, une passe dédiée aux **erreurs de raisonnement** :
comparaisons qui ne peuvent pas être vraies, colonnes inexistantes, contraintes
qui contredisent le modèle métier. Cette classe de défauts ne produit ni
exception ni alerte — le code répond, avec une valeur fausse.

## R1 — Le bulletin du secondaire ne s'affichait jamais *(critique)*

`EleveController::bulletin` orientait vers le bon calcul par
`$classe->categorie_classe === 'secondaire'`. La valeur stockée est
`Secondaire`. En PHP `===` est sensible à la casse : la condition était
**toujours fausse**, donc tout élève du secondaire recevait le bulletin
maternelle/primaire — un calcul différent, sans coefficients ni séries.

Cause racine : `classes.categorie_classe` était écrit capitalisé par
`ClassesController` et les seeders, mais interrogé en minuscules par
`NotesController`, `typeEvaluationController` et `periodesController`. Cela ne
« marchait » que par la collation insensible à la casse de MySQL ; les mêmes
requêtes ne renvoient rien en SQLite, sur quoi tourne la suite de tests.

Corrigé par `App\Support\Cycles` (vocabulaire unique, `normalise()`,
comparaison `is()` insensible à la casse), un mutateur sur `Classes`, une
migration de normalisation des données, et la règle de validation dérivée du
même vocabulaire.

## R2 — Trois chefs de cycle provisionnés puis verrouillés *(critique)*

`SchoolProvision` crée un compte `directeurM`, `directeurP` et `directeurS`
pour chaque école, `AdminUsersSeeder` leur attribue un mot de passe. **Aucune
des 87 routes gardées ne nommait ces rôles** — toutes lisent `role:directeur`.
Les trois comptes ne pouvaient atteindre aucun endpoint, ni passer aucune
policy. `DashboardController` et `NotesController` avaient chacun développé
leur propre liste de contournement ; les policies, non.

Corrigé par `App\Support\Roles` : un rôle appartient à une **famille**, et
garder sur la tête de famille admet ses membres. `role:directeur` couvre
désormais les chefs de cycle sans que chaque route les énumère. La famille ne
couvre que les chefs d'établissement — un chef de cycle n'est ni comptable, ni
infirmier, ni super-admin (cf. S1).

## R3 — Deux policies structurellement infranchissables

- `ElevePolicy::view` et `AbsencePolicy::view` filtraient sur
  `eleves.classe_id`. La colonne est `class_id` : la comparaison portait sur
  `null`, donc **aucun enseignant ne pouvait voir aucun élève**.
- `NotePolicy` lisait `$note->enseignant_id`, en le comparant à la fois à
  `$user->id` et à `$user->enseignant?->id` — comme pour couvrir les deux
  espaces d'identifiants possibles. La table `notes` n'a pas de colonne
  `enseignant_id` : l'auteur est `created_by`. L'expression valait
  `null === int || null === int`, et **aucun enseignant ne pouvait consulter ni
  modifier une note**, pas même celle qu'il venait de saisir. La comparaison
  double masquait l'erreur en ressemblant à un repli délibéré.

## R4 — Le rang, silencieusement faux

`BulletinService` plaçait l'élève avec `Collection::search()`, qui renvoie
`false` quand la valeur est absente. `search(...) + 1` valait donc `1` :
**toute erreur de calcul déclarait l'élève premier de sa classe**. Le rang était
par ailleurs établi sur des notes brutes de barèmes différents.

`NotesController::classement` définissait le rang autrement encore — `$index + 1`
sur une liste triée, donc trois moyennes identiques recevaient les rangs 1, 2 et
3, en contradiction avec le bulletin des mêmes élèves.

Les deux calculs partagent désormais la même sémantique : moyenne ramenée sur
20, ex æquo au même rang, et `null` — non pas 1 — quand l'élève ne peut pas être
placé.

## R5 — Le coefficient faisait échouer tout le bulletin du secondaire

`getCoefficient()` interrogeait `classe_matiere` (singulier). La table est
`classe_matieres`. Chaque appel levait une exception, donc l'endpoint entier
échouait. S'y ajoutaient `$eleve->classe_id` et l'absence de filtre sur
`ecole_id` dans une requête `DB::table()`.

## R6 — Contournement du scope tenant

`NotesController` atteignait des tables scopées par `DB::table()` — ce que le
CLAUDE.md interdit explicitement — à 18 endroits. Deux étaient atteignables :

- `classement($classeId, $periode)` classait la classe dont on lui passait
  l'identifiant : un directeur pouvait lire le **classement nominatif d'un autre
  établissement**.
- l'import CSV appariait les élèves sur `numero_matricule` sans filtre d'école :
  une **écriture inter-tenant** en cas de matricule identique.

Les 16 autres appartenaient à quatre méthodes `repartitionNotes*` sans aucune
route — code mort, mais qui aurait constitué une fuite le jour de son câblage.
Consolidées en un calcul scopé, en une requête au lieu de quatre, avec des
tranches contiguës (`0-5`, `5-10`, `10-15`, `15-20` : une note à 5,5 n'était
comptée nulle part) et une normalisation sur `note_sur`.

## R7 — L'intégration d'une deuxième école était impossible

Sept identifiants attribués par l'école portaient un index UNIQUE **de portée
plateforme**. Deux bloquaient l'onboarding :

- `type_evaluations.nom` — une seule école au monde pouvait avoir un `Devoir1` ;
- `paiement_methods.method_name` — une seule pouvait proposer `Mobile Money`.

Les cinq autres (`eleves.numero_matricule`, `etudiants.matricule`,
`certificats.numero_certificat`, `paiement_invoices.invoice_number`,
`paiement_receipts.receipt_number`) échouent au premier conflit : deux écoles
numérotant leurs élèves depuis `MAT-001` ne peuvent pas coexister.

Rendus uniques **par école**. Restent volontairement globaux : `users.email`,
`users.identifiant`, `utilisateurs.nom_utilisateur` (identités de connexion —
un identifiant doit résoudre vers un seul compte), `payments.transaction_id`
(émis par le prestataire) et `vehicules.immatriculation` (unique nationalement).

# Troisième passe — conception du cloisonnement (2026-08-03)

Cette passe ne corrige plus des bugs : elle construit la frontière d'accès qui
manquait. Détail de conception dans `CONCEPTION_CLOISONNEMENT.md`.

## C1 — Le cloisonnement par cycle ne reposait sur rien

La passe précédente avait ouvert `role:directeur` aux chefs de cycle, en notant
que la séparation reposait sur le fait que chaque tableau de bord appelait ses
propres endpoints. **C'était faux** : aucune route nommée par cycle n'existe, et
le front n'en appelle aucune. Rien ne séparait les trois cycles.

Le front avait pourtant le bon modèle — `ROLE_NORMALIZATION` mappe les trois
sous-rôles vers `directeur`, « les sous-rôles n'ont pas de dashboard distinct ».
L'intention était : même interface, données cloisonnées par le serveur. C'est la
moitié serveur qui manquait.

Construit : `CycleAccess` (résolution du périmètre, une fois par requête),
`ScopedToCycle` (global scope + garde d'écriture, chemin déclaré par modèle),
`OutsideCycleException` (403 rendu par l'exception elle-même). Appliqué à onze
modèles ; les 54 tables sans cycle restent partagées, un chef de cycle devant
voir les ressources d'établissement.

Le cache du périmètre est adossé au **conteneur**, pas à une statique : la
première version fuyait entre tests — échec en suite, succès en isolation.

## C2 — `catch (\Exception)` transformait 403 et 422 en 500

50 méthodes de contrôleur enveloppent leur corps dans un `catch (\Exception)`
répondant 500. `AuthorizationException` étant une `\Exception`, cinq de ces blocs
transformaient un refus d'autorisation légitime en panne serveur : le client ne
pouvait pas distinguer « vous n'avez pas le droit » de « le serveur est cassé ».

`Controller::rethrowIfMeaningful()` rend l'exception au framework quand elle
porte déjà sa réponse — autorisation, authentification, validation,
enregistrement introuvable, HttpException, `OutsideCycleException`. Inséré aux 50
sites.

## C3 — L'enregistrement d'un paiement échouait à 100 %

`POST /api/comptable/paiements` exigeait `type_paiement`, que la table ne portait
pas, puis le passait à `create()` :

```
SQLSTATE[HY000]: table paiements has no column named type_paiement
```

`reference` était dans la même situation, alors que `PaymentController` en génère
une, que deux classes de requête la valident, que `PaiementResource` l'expose et
que l'événement `PaiementConfirmed` la transporte. Le front lit `type_paiement`
sur deux pages. Chaque couche supposait ces champs sauf la table : les deux
colonnes sont ajoutées. L'endpoint collecte désormais aussi `mode_paiement`
(NOT NULL, et une écriture comptable sans mode de règlement n'est pas
rapprochable) et dérive le solde au lieu de le laisser nul.

## C4 — 122 règles `exists:` contournaient le scope tenant

La règle `exists:` de Laravel interroge le query builder brut et ne voit donc pas
`BelongsToEcole`. 122 règles sur 37 fichiers acceptaient un identifiant de
n'importe quel établissement — et comme la validation *passait*, l'écriture
partait ensuite avec une clé étrangère pointant chez un autre tenant. Cas
concret : un comptable pouvait enregistrer un paiement sur l'élève d'une autre
école.

`school_exists:` (`App\Validation\SchoolExistsRule`) borne l'existence à
l'établissement. La contrainte `ecole_id` n'est ajoutée que si la colonne existe,
vérifié contre le schéma vivant — les tables plateforme (`tenants`, `plans`,
`modules`, `ecoles`) ne sont pas filtrées, et une table qui gagnerait `ecole_id`
serait couverte sans modification. `users` reste sur `exists:` : le trait
`BelongsToEcole` l'ignore explicitement, l'identité de connexion étant
plateforme-wide.

## C5 — Colonnes fantômes dans les modèles et les Resources

Un test compare désormais chaque `$fillable` au schéma. Il a trouvé :

- `EmploiDuTemps` — `class_id` déclaré, la colonne est `classe_id`. Aucune
  création par assignation de masse ne pouvait aboutir.
- `PaiementEleve` — `statut` (la colonne est `statut_global`), plus
  `type_paiement` et `reference`, absentes. `ProcessPaiementJob` marquait un
  paiement en échec sur `statut` : sans effet.
- `EcoleResource` — lisait `statut` alors que la colonne est `status`, avec un
  repli `?? 'active'` : **toute école était rapportée active**, y compris celle
  qu'on venait de désactiver.
- `UserResource`, `EleveResource`, `ClasseResource`, `PaiementResource` — une
  quinzaine de champs lus sur la mauvaise table ou inexistants. Les cinq
  Resources ne sont référencées par aucun contrôleur ; corrigées plutôt que
  supprimées, parce que mortes *et* fausses elles piègent le premier qui les
  câble.

## T1 — La production affichait une page blanche *(critique)*

Uncaught ReferenceError: Cannot access 'j' before initialization

# Quatrième passe — durabilité des dossiers (2026-08-05)

## D1 — Supprimer un élève effaçait tout son dossier scolaire

`EleveController::destroy` faisait `$eleve->delete()` puis `$user->delete()`,
deux suppressions dures, et **18 tables cascadaient sur `eleves.id`** ; quatre
autres sur `etudiants.id`. Un seul appel effaçait notes, absences, paiements,
moyennes, dossier médical, vaccinations, emprunts, bourses, certificats,
rendez-vous, inscriptions aux examens, diplômes — et le compte de connexion.

C'est le défaut des 62 cascades sur `ecole_id` (voir la première passe), un cran
plus bas, et il reçoit la même réponse, parce que cette réponse était la bonne :
**on désactive, on ne supprime pas.**

**Portée réelle** — l'API principale n'expose aucune route DELETE pour les
élèves ; `destroy` n'était atteignable que par l'`apiResource` de la surface
tenant. Le défaut était donc plus étroit que le nombre de cascades ne le
suggère, mais catastrophique quand il était atteint.

**Construit**

- `eleves.statut` et `etudiants.statut` (`active` / `inactive`), plus
  `deleted_at` sur les deux. Les deux mécanismes ne sont pas redondants : le
  statut dit « n'est plus inscrit » — la fiche reste listée, cherchable,
  consultable ; la suppression douce dit « n'aurait jamais dû exister » et
  retire de toutes les requêtes. Confondre les deux perd l'information.
- Les 22 contraintes passées en `RESTRICT`. La cible de chaque clé est relue
  depuis le schéma vivant, car trois colonnes s'appellent `eleves_id` au pluriel
  (`eleves_matieres`, `moyennes`, `paiements`) — la recréer avec un nom deviné
  l'aurait silencieusement pointée vers rien.
- `destroy` délègue à `deactivate`, plus `activate`, sur les deux contrôleurs.
  Le compte perd son accès (`is_active = false`) mais survit : le supprimer
  effacerait l'identité de connexion et, `communications.auteur_id` étant
  désormais en `SET NULL`, orphelinerait ce que la personne a publié.
- Vocabulaire volontairement réduit à `active` / `inactive`. Les motifs de
  départ — transfert, diplôme, radiation — sont une question produit que
  personne n'a posée ; figer un enum maintenant serait répondre avant la
  question.

**Un piège rencontré** — `$eleve->user->update(['is_active' => false])` ne
faisait rien. `is_active` est hors du `$fillable` de `User`, délibérément :
l'état d'un compte ne doit pas se régler depuis une charge de requête. Un
`update()` l'écartait donc en silence et la désactivation ne coupait aucun
accès. Corrigé par affectation directe. Au passage, le `$guarded` de `User` est
**inerte** — Eloquent ne le consulte que si `$fillable` est vide — ce qui est
maintenant documenté dans le modèle : la protection réelle venait de l'absence
du champ dans `$fillable`.

## D2 — Deux cascades introduites par les nouvelles fonctionnalités

Les migrations du module universitaire et des annonces respectaient bien
`ecole_id => restrictOnDelete`, mais deux contraintes échappaient à la règle
parce qu'elles portaient sur une *autre* colonne — et `User` comme `Etudiant`
